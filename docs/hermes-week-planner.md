# Hermes week planner

A separate `week-planner` Hermes profile reasons over owner-only, plain-language rules and events from the authenticated Google account. Its weekly Hermes **agent cron** and interactive chat use the same four calendar tools: read one week, create a private block, move a planner-owned block, and append an explicit lasting rule. No fixed-slot Python scheduler or Compose cron runs this profile.

The calendar MCP server holds Google OAuth credentials under that profile's private `HERMES_HOME`. It checks the authenticated primary calendar against the account in the private boundary and resolves **one uniquely owned** calendar by name before every session. It reads event times and titles across all subscribed calendars, including hidden ones. Tools have no calendar-ID argument for writes; they write only tagged, private events on the resolved target, never invite attendees, and reject busy slots. `create_block` uses deterministic IDs so a retry or a manually moved block is not overwritten; a manually deleted block is not recreated. `move_block` requires a planner-owned ID and an ETag. Availability is checked immediately before a write, but Google Calendar has no cross-calendar transaction: a concurrent human edit can still create a conflict that needs manual resolution. Event titles are untrusted data, not instructions.

The identity boundary remains in `~/.config/ai-pr-automation/week-planner.md` (owner-only). Conversational preferences are in `~/.config/ai-pr-automation/week-planner-notes.md`, also owner-only. Only an explicit request for a standing rule should cause `remember_rule` to append to that file. A one-off calendar move does not rewrite recurring preferences. The old structured planner prototype is inactive and its files are not deleted.

## Setup (not automatic)

1. Run `bash scripts/week-planner-install.sh --install` from this checkout, then `bash scripts/week-planner-install.sh --check`. On a fresh account it creates the restricted profile, writes only local paths to its owner-only `.env`, and creates **one paused cron**. On an existing profile it preserves the cron and refuses config or path drift instead of overwriting edits. If you move or merge the checkout, update the profile's script path yourself and test `hermes -p week-planner mcp test week-calendar` before removing the old checkout. The profile loads one calendar MCP server; do not enable terminal, file, code-execution, browser, or other unrestricted tools.
2. Create a Desktop OAuth client in your Google Cloud project and enable the Calendar API. Store its JSON at `~/.hermes/profiles/week-planner/google_client_secret.json` with mode `0600`. Run `python3 scripts/hermes-week-calendar-auth.py` from this checkout **locally**. The browser asks for **Calendar only**; the helper verifies the authenticated primary account and uniquely owned target before saving `google_token.json` (`0600`). The installed Hermes Google Workspace setup script requests Gmail/Drive/Docs as well, so do **not** use it for this profile or attach its broad skill. Never paste the client JSON, redirect URL, or auth code into chat. Google's Calendar scope grants account-wide event-write access, but the MCP code permits writes only to the verified target calendar.
3. Verify the authenticated primary account, unique target calendar, profile tool list, and a synthetic calendar-tool test before any live schedule. Missing OAuth or an ambiguous calendar name stops the MCP server; it must not silently fall back to `primary`.
4. `hermes -p week-planner cron list --all` shows the paused job created by the installer. After one-time validation, resume that job; do not create a duplicate. The existing personal Hermes gateway multiplexes this profile and ticks its cron jobs—do not start a second gateway. The cron fires on the host's local clock; keep the host in `America/New_York` for a 17:00 New York trigger.

After the first scheduled run, inspect `hermes -p week-planner cron runs <job-id>` and the primary calendar. The fake-calendar tests and MCP discovery check do not prove the model produced a good live week. If it fails, pause with `hermes -p week-planner cron pause <job-id>`; retries should reuse stable event keys rather than create new ones.

Chat through `hermes -p week-planner chat`: “Move my planner workout to Thursday at 7pm” makes a one-off change; “From now on, keep Sunday afternoons free” records a standing preference. Automatic calendar writes require no per-run approval, but changes outside the single target calendar are not supported. The configured provider receives rules and calendar event details when this profile runs; do not enable it without consent.
